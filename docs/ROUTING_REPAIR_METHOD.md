# 実配線GDSの修復・検証手順

最新のコア結果は[CORE_ROUTING.md](CORE_ROUTING.md)。短絡・断線0、公式LVS一致まで確認した。以下は途中候補も含む採否判定の方法である。

この文書は、配置配線済みGDSのトップセル配線だけを実験的に修復するための設計内フローを記録する。APRtoolsの配線機能を置き換えるフローではなく、APRtoolsやPDKへの更新・修正も含まない。固定されたツールチェーンとGDSを入力に、候補差分を独立検証する。

## 入力を固定し、候補を隔離する

各実験は専用の `experiments/<name>/config.py` と `build/` を持つ。`MAZE_ROUTE` には入力GDSのパスとSHA-256、対象ネット、削除するトップ階層配線矩形の形状インデックス、削除via位置、探索範囲・格子、実ピン・配置・形状マップ、基準DRCレポートを明記する。設定はバージョン管理対象のリテラル辞書として検証器がASTから読み、任意のconfigコードを実行しない。

まず `python3 scripts/check_toolchain.py` を実行し、その後に `scripts/maze_route.py` または該当実験の専用ジェネレーターを使う。ジェネレーターは入力GDSのハッシュを事前・事後に検査し、入力を上書きせず `build/candidate.gds` とマニフェストへ出力する。マニフェストには入力・設定・生成器・ソルバー・形状データ・実ピン・配置・固定ルールのハッシュ、削除形状、追加形状、探索経路を記録する。GDSの書き出しでは `SaveLayoutOptions.gds2_write_timestamps = False` を指定する。GDS内の書き出し時刻が変わるだけでも候補ハッシュが変わり、同一形状の再生成確認や後段のハッシュ結合を妨げるためである。

候補編集はトップセルのトップ階層M1/M2矩形とroute viaインスタンスに限定する。`scripts/prune_route_boxes.py` は既存トップ階層のM1/M2矩形を同一レイヤ・同一bboxでまとめ、候補を一群ずつ削除する。`scripts/prune_route_vias.py` はトップ階層route-via配置群を候補にする。どちらも形状マップとの接触・重なりは候補抽出の手掛かりにとどめ、採否は実GDSから再抽出した接続性で決める。セル内部形状、標準セル、階層、APRtoolsスクリプトは編集しない。

2層迷路ルーター (`scripts/maze_route.py`, `scripts/maze_grid.cpp`) は、対象ネットの既存route矩形と選択したviaだけを外し、実GDS内の他ネット配線・セル形状を障害物としてM1/M2の直交経路を探索する。クリアランス、金属幅、via enclosure、GC/CO/V1近傍禁止領域は固定 `rules.py` と現行DRC deckから取得する。格子上の経路は探索候補であり、配置済み全ネットの合法性を保証するものではない。ピン中心が探索格子に乗らない端点では、`terminal_extensions` に明示した直交延長を加えることがある。延長幅は対象金属の幅から決め、公式DRCと実ピン監査を必ず再実行する。格子に合うよう端点を丸めてピン接続を推定してはならない。

## 接続性を実形状から監査する

形状マップ (`net_shapes.json`) の線分や近接ピンアンカーは、既存配線を見つけるためのヒューリスティックである。監査の正本にはしない。`scripts/routing_diagnostics.py` は固定v59_4 LEFの各セル端子矩形を配置データで実座標へ変換し、GDS上の対応する層・実端子図形を検査する。候補検証器はソースと候補の両方についてこの完全な実ピン・形状監査を実施する。今回の対象チェックポイントでは421配置インスタンスと987信号ピンが一致し、全端子形状に欠落がなく、未接続ネットが0件であることを要求する。座標アンカーだけから作った簡易ネットリストとの混同を避ける。

さらに `scripts/prune_route_vias.py` のKLayout `LayoutToNetlist` 抽出を実GDSのM1/M2/V1/GC/COへ適用し、LEF層に従って端子点をprobeする。GC/COを含む接続を扱い、VDD/VSSの実セルラベルから電源railごとの連結成分数と接続された信号名も調べる。ネット同一性比較には `Net.expanded_name()` を使う。階層抽出結果の匿名子回路名（例 `$1`）だけでは別の階層に同名ノードが存在し得るため、短絡判定にその表示名だけを使わない。

採用候補は、ソースと比較して短絡ネット対の集合が**真に減少**し、新しい短絡対がなく、未接続・ピン欠落がなく、VDD/VSS成分数と各railに接続する信号名が維持される必要がある。さらにインスタンスの階層・配置、全非トップセルの形状と子インスタンスが同一で、変更レイヤがトップ階層配線M1/M2/V1に限られることを確認する。標準セル内部形状やピン形状を配線差分として変更する修復は受け入れない。

## 公式DRCと検証結果の読み方

各改善候補に対し、固定wrapper経由で公式drawing DRCと公式MDPを実行し、候補のマーカー集合が凍結ソースのマーカー集合の部分集合であることを要求する。既知の違反があるとwrapperの終了コードは1になり得るため、終了コードだけを合否にしない。一方、古いレポートが残っている状態での成功判定も禁止する。検証器は対象のdrawingレポート、GDS stemから生成される `<stem>_mdp.lyrdb`、MDP出力GDS、ログを事前に削除し、新規生成されたこととログ中のdrawing/MDP実行要約を確認する。drawing用 `-r` レポートとMDPレポートは別ファイルである。MDP出力は `--mdp-gds` に指定した任意名と同じとは限らず、入力GDSのstemに結び付く。ソースと候補は異なるstemのコピーを使い、レポートの取り違えや上書きを防ぐ。

この比較で受け入れられても、残存違反がゼロとは限らない。ポート注記前の配線修復基準では、既知ソースに存在する2件の `GC.ANT` drawing markerと2件の `WAR06: Floating SG Detected` MDP markerが残る。候補も同じマーカー集合であることは「この差分が新たなmarkerを導入していない」という比較結果であり、DRC-clean、LVS合格、製造signoffを意味しない。完全LVSやPEXの実行・合格もこの検証器は主張しない。最終コアへの正しいポート注記と回路LVSは別の検証記録に分けた。

標準ではソースと候補のbbox完全一致を要求する。例外的に `MAZE_ROUTE.max_core_size_um: [幅, 高さ]` を明示した実験だけは、候補bboxが指定予算内であることを検査し、ソース・候補bboxと各辺の成長量を記録する。この指定はフレームやパッケージへの適合を確認するものではない。たとえば `experiments/maze_233_margin` は1786.5 × 1760.3 µmで1800 × 1800 µm予算内だが、これは実装フレームに収まるという判定ではない。最終テンプレートの外形・ピン配置との統合確認は別工程である。

## 実行例・レポート・来歴

標準の候補生成と検証は次の順で行う。下記の `experiments/new_trial` は、新しく作ってconfigを記録する実験ディレクトリを表す。後段が参照する凍結済みの実験ディレクトリへ再生成して上書きしない。

```sh
python3 scripts/check_toolchain.py
.venv/bin/python scripts/maze_route.py --design-root experiments/new_trial
.venv/bin/python scripts/validate_route_candidate.py --design-root experiments/new_trial
```

まずconfigの `source_gds` と `source_sha256` をレビューし、そのハッシュの入力から候補を再生成する。候補生成後に設定や入力を変更した場合、候補とマニフェストを同じ設定で再生成してから検証する。検証レポートは `build/verification.json` に入力、候補、config、検証器、DRC deck、監査データ、各レポートのハッシュとチェック結果を保存する。候補の `ACCEPTED` は、そのレポートに記載された**指定ソースからその候補への差分条件**を満たしたという意味に限定される。

記録例：

- `experiments/maze_040/build/verification.json` は `_040_` / `_058_` の短絡対を45対から44対に減らし、drawing/MDPの既知2件を維持した例。
- `experiments/maze_h1/build/audit/verification.json` は44対から43対への独立監査記録。同実験の `build/verification.json` に残る `ERROR` は開発途中の検証器で `run_drc` の引数が不整合だった記録で、ソース不一致の記録ではない。実験ごとのREADMEに従い、エラーの原因と対象レポートを区別する。
- `experiments/maze_233_margin/build/verification.json` は `_222_` / `_233_` を21対から20対に減らした例。bbox成長を許可する明示的なサイズ予算とbbox前後値を持つ。
- `experiments/maze_cumulative/` は短絡数が17対から13対に減った一方、新規 `_103_` / `_162_` が発生したため不採用となった例。そこから派生した `maze_038` が親候補に対して13対から10対へ減り局所検証に通っても、拒否済み親に由来するため採用可能な全体チェックポイントにはならない。

したがってpair数の最小値や個別候補の `ACCEPTED` 表示だけで候補を統合しない。最終候補は採用可能な凍結祖先から差分を再構成し、その祖先に対して新規短絡なし・未接続なし・電源同一性・完全な実ピン監査・公式drawing/MDP marker部分集合を改めて確認する。個別レポートは親子の来歴とソースhashが一致して初めて一連の修復として扱える。
